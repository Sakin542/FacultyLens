## UAT-001 — In-app navigation away from Assessment Details freezes the view

| Field | Detail |
|---|---|
| Scenario | S04 (assessment detail links), S11 (Generate Questions), S12 (Blueprint), S13 (Versions); also every sidebar link |
| Severity | **BLOCKER** |
| Steps | 1. Sign in. 2. Open any assessment (`/assessments/:id`), wait for it to load. 3. Click **Blueprint**, **Versions**, **Generate Questions**, **View Submissions**, the breadcrumb, or any sidebar item (Courses, Analytics…). |
| Expected | Target page renders. |
| Actual | Browser URL changes (e.g. `/assessments/20/blueprint`, `/courses`) but the Assessment Details page stays on screen indefinitely; the sidebar highlights the new item. Only a full browser reload shows the target. Reproduced deterministically on 8 of 8 attempts across three runs and three probe scripts; navigation from Dashboard, Courses, Course Details, Submissions, Analysis and Analytics pages works normally, so the trigger is specific to `AssessmentDetails`. |
| Impact | The assessment page is the hub of the faculty workflow (Blueprint → Generate Questions → Rubric → Versions → Submissions). A faculty member who does not know to press F5 is stuck; nothing on screen explains why. This is why S11 and S12 could not be reached by clicking in run #2 and why the walkthrough had to fall back to typed URLs (recorded in the observations as "faculty had to reload"). |
| Reference | `uat-results/S04-nav-after-blueprint-click.png`, `S04-nav-after-sidebar-click.png` (URL `/courses`, sidebar "Courses" highlighted, assessment content still displayed); observation `S04 · in-app links … render the target page without a reload — FAIL`. |
| Root cause (verified) | `frontend/src/App.tsx` enables React Router's `future.v7_startTransition`. On `AssessmentDetails` the route change is wrapped in `startTransition` and the transition never commits (the page keeps several polling/derived effects alive — `useExplanationModal`, submission summary, collaboration comments — that keep the transition pending). A diagnostic build with `v7_startTransition: false` navigated correctly from the same page in every probe; the change was **reverted** so UAT reports on the delivered build. Why STEP 41 missed it: every journey spec navigates with `page.goto(...)`, which is a full load, never an in-app click. |
| Suggested fix | Either drop `v7_startTransition` (one-line, verified) or make `AssessmentDetails` transition-safe (avoid state updates that keep the transition pending during unmount). Add a Playwright regression test that *clicks* `blueprint-link` / a sidebar item from `/assessments/:id` and asserts the target renders. |
| Status | FIX_VERIFIED_NOT_APPLIED |

## UAT-002 — No manual question entry; the UI implies there is

| Field | Detail |
|---|---|
| Scenario | S04, S05 |
| Severity | MAJOR |
| Steps | 1. Create an assessment. 2. On `/assessments/:id` look for a way to type in a question. 3. Read the empty state. 4. Open **Upload Question Paper**. |
| Expected | Faculty can add a question directly (text, type, marks, difficulty, Bloom, LO), or the UI states clearly that questions come only from the generator. |
| Actual | There is no add/edit question form for official assessment questions (no `POST /assessments/{id}/questions` route exists — questions are created solely by `generated-questions/{id}/add-to-assessment`). The empty state says *"Manage course questions in the Question Bank or review assessment history"* and links to the **Question Bank**, which is the archive of *previous* exam questions and cannot add a question to this assessment. **Upload Question Paper** only stores the file (`AssessmentQuestionPaperController::store` does no extraction); the course-page document uploader promises *"Automatic Text Extraction … to extract syllabus units, assessment questions"*, so faculty reasonably expect uploaded papers to become questions. Faculty who already have a paper written must re-create it through the AI generator, editing each draft to match. |
| Impact | Core task ("add my questions") is not completable as most faculty would attempt it; three signposts point the wrong way. Acceptance of S05 therefore hinges on the generator path. |
| Reference | `uat-results/S04-assessment-detail-empty.png`; observation `S04 · assessment detail page … NOTE: empty state points to "Question Bank"`; `S05 · there is no manual add-question form`. |
| Suggested fix | Add a minimal manual question form (or "add from paper" extraction) — or, at minimum, rewrite the empty state to "Questions are added through **Generate Questions** (AI drafts you approve). Upload Question Paper only attaches the file." and remove the questions promise from the upload note. |
| Status | OPEN |

## UAT-003 — Question cards hide faculty-owned metadata and show raw enums

| Field | Detail |
|---|---|
| Scenario | S05, S08 |
| Severity | USABILITY |
| Steps | 1. Add three questions (CLO2, descriptive, Apply, 10 marks). 2. Open `/assessments/:id`. 3. Override Q1's Bloom level to *Analyze* via **Why? → Override**. 4. Look at the Q1 card. |
| Expected | Each card shows the question's mapped CO/LO, its type, marks, difficulty and Bloom level as set by faculty, and reflects the override. |
| Actual | Cards show text, marks and difficulty, plus post-analysis **AI** badges (`AI: DESCRIPTIVE`, `AI: PROBLEM_SOLVING`, `BLOOM: APPLY`, `AI: MEDIUM`). The mapped outcome (CLO2) is not shown anywhere on the card; question type appears only as the AI's raw enum with underscores; there is no faculty Bloom value, and after the override the card still reads `BLOOM: APPLY` (the AI value) — the faculty decision is visible only inside the explanation dialog ("Current faculty value: Analyze") and in the version snapshot. |
| Impact | Faculty cannot verify LO coverage or their own decisions at a glance; AI values visually dominate faculty values, which cuts against "AI assists, faculty decides". |
| Reference | `uat-results/S05-question-list-FAIL.png`, `A11Y-mobile-assessment.png`, `S13-version-finalized-FAIL.png` (version page *does* show `Descriptive · Medium · Analyze · CLO2`). |
| Status | OPEN |

## UAT-006 — Hand-rolled modals fail basic dialog accessibility

| Field | Detail |
|---|---|
| Scenario | S02 (Add Course), S03 (Add/Edit Learning Outcome), S06 (Upload Academic Document, Upload Question Paper), S09 (Accept/Dismiss recommendation) |
| Severity | MAJOR (accessibility) |
| Steps | 1. `/courses` → Tab to **Add Course** → Enter. 2. Press Escape. 3. Run axe. 4. Repeat on the outcome and upload dialogs. |
| Expected | `role="dialog"`/`aria-modal`, focus moves into the dialog, Escape closes, every control labelled, close button named. |
| Actual | Add Course: no `role="dialog"` (count 0), focus stays on the trigger, **Escape does nothing**; axe: `button-name` ×1 (icon-only ✕) and `select-name` ×2 — both **critical**. Learning Outcome dialog: `<select>` and `<textarea>` have visual labels without `htmlFor` (walkthrough check "controls without a label: select, textarea"). Document upload dialog: same unassociated labels. Question-paper upload and recommendation feedback dialogs: icon-only close button with no accessible name. (Contrast: `VersionCreateDialog`, `ExplanationModal`, `RubricGenerator`, `CreateSubmissionModal` do it right — the pattern exists in the codebase.) |
| Impact | Keyboard and screen-reader users cannot reliably operate the first two workflows (course, outcomes). |
| Reference | observations `A11Y · keyboard-only … Escape does not close the Add Course dialog (focus moved into dialog=false, role=dialog count=0)`, `S03 · outcome form fields have programmatic labels — FAIL`, axe `/courses`. |
| Status | OPEN |
